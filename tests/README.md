# pacemaker_sim Characterization Test Suite

Generated by the Verification & Test Agent stage of the AEGIS-derived
Legacy Modernization pipeline. Purpose: unblock the Test Coverage
dimension of the Risk & Triage matrix (Section 3 of the master
orchestrator prompt), starting with the lowest-coupling, then the
non-deterministic, modules.

## What this is

**Characterization tests, not spec-conformance tests.** They pin the
*current, observed* behavior of the real, unmodified source files -
including behavior the source code's own comments call a smell, and in
two cases, behavior that a refactor could plausibly get wrong without
ever knowing it was wrong. That's intentional: a refactor should have
to break one of these assertions *on purpose*, with a reviewed
follow-up change to this file, rather than silently drifting behavior
underneath an AI agent's changes.

Every suite links the real target `.c` file against the real, unmodified
rest of the codebase rather than mocking global state - nothing about
struct layout, global storage, or constants is guessed.

No file outside `tests/` was created or modified to produce this suite -
including for `sensing.c` and `battery.c`, whose determinism problem is
solved with a test-only linker trick (see below), not a source patch.
The build file is named `tests.mk`, not `Makefile`, so it stays out of
the top-level build's discovery path (opt-in, not part of `make all` at
the project root).

## The determinism fix for `sensing.c` / `battery.c`

Both modules seed a hand-rolled LCG PRNG from `time(NULL)` in their
`_init()` functions - confirmed during Discovery as the root cause of
the pacemaker_sim binary producing different output on two runs with
identical arguments. Naive "capture current output as the golden
baseline" characterization testing doesn't work against a moving target.

**The fix, `fake_time.c`, is a test-harness-only linker trick, not a
source change.** It defines its own `time_t time(time_t *tloc)` with
the standard libc signature. Because every test binary here compiles
directly from the `.c` sources rather than linking a prebuilt `libc.so`,
the linker resolves every call to `time()` - including the ones inside
`sensing.c` and `battery.c` - to this local definition instead of pulling
it from the libc archive. `test_set_fake_time(v)` then controls exactly
what every subsequent `time(NULL)` call returns, for the lifetime of the
process. `sensing.c` and `battery.c` are completely unaware this is
happening; nothing in either file changes.

This was verified empirically before relying on it: two runs seeded
identically via `test_set_fake_time()` produce byte-identical output;
different seeds produce different output (see
`test_determinism_itself()` in both `test_sensing.c` and
`test_battery.c`). **This must never be linked into the real
`bin/pacemaker_sim` build** - it isn't; that build uses the top-level
`Makefile`, which `tests.mk` and `fake_time.c` never touch.

If this determinism problem needs solving for the *real*, non-test
codebase (e.g. for a future CI environment that wants reproducible
simulation runs), the same idea - an injectable seed override, gated
behind a build flag or environment variable - would be the natural
follow-up, but that is a source change and was deliberately kept out of
scope here given this engagement's zero-source-modification posture for
characterization work.

## Notable finding: comment/code drift in `telemetry.c`

`evt_flag_desc()`'s header comment states it "only describes the single
most 'interesting' bit set... if multiple flags are set the others are
just silently not described." **The actual code does not do this** - it
uses six unconditional `if` checks (not an `if`/`else if` chain), so
when multiple event flags are set, *all* of their names are concatenated
into the description string. `test_evt_flag_desc_comment_drift()`
captures real `stdout` from `telemetry_dump_log()` and proves both flag
names appear together.

This was not one of the ~9 smell categories the codebase's own
documentation calls out. It matters because a refactor agent that took
the comment at face value as the intended spec (rather than the verified
behavior above) would "fix" the code to match the comment, silently
changing output format for every multi-flag event.

## Notable finding: cross-module log-index divergence in `arrhythmia.c`

`arrhythmia_run_ams_logic()` tags a mode-switch event by writing directly
to `g_log[g_log_count % MAX_LOG_ENTRIES].flags`. But `telemetry.c` - the
module that actually owns the log ring buffer - computes its write and
"most recent" indices using `g_log_head` as well:
`(g_log_head + g_log_count) % MAX_LOG_ENTRIES`. These two formulas only
agree while `g_log_head == 0`, i.e. before the ring has ever wrapped.

`test_ams_log_flag_indexing_diverges_after_wrap()` drives the log past
its first wraparound (any realistically long-running session) and shows
the two indices land on different slots - the `EVT_MODE_SWITCH` tag ends
up on a stale, unrelated log entry instead of the one for the tick when
the switch actually happened. This is a real, latent bug from
`arrhythmia.c` reaching into a data structure it doesn't own, using a
different indexing convention than the module that does - worth an
Architecture & Decoupling Agent decision (preserve for device parity vs.
fix consciously) before Code Generation touches either file.

## Notable finding: `mode_step()` is dead code

`modes.c`'s `mode_step()` carries a header comment claiming it is
"presently only used for CLI dry-run mode checks in main.c."
`grep -rn "mode_step" src/ include/` shows exactly one match outside
`modes.c` itself: its own prototype in `pacer.h`. **It has zero call
sites anywhere in the codebase** - not in `main.c`, not in
`pacer_core.c`. The real pacing state machine that actually runs
(`pacer_core_handle_state()` in `pacer_core.c`) independently
re-implements the same per-mode timing logic `mode_step()` contains,
which is consistent with the file's own comment describing this as a
parallel implementation added by "a different engineer who didn't want
to touch the scary state machine file."

`mode_step()` is still fully characterized in `test_modes.c` (100% line
coverage, all 12 modes plus the unrecognized-mode fallback) despite
being unreachable in practice: it is part of `modes.c`'s public API
surface per `pacer.h`, and a refactor agent needs a ground-truth
baseline for it before deciding whether to drop it, wire it in, or
explicitly retain it as documented dead code. Flagged for the
Architecture & Decoupling Agent to make that call before Code
Generation touches `modes.c`.

`test_modes.c`'s capability-predicate suite includes a cross-check
confirming a truth-table property (`atrial_paced` XOR
`ventricular_paced` for every single-chamber mode) that turned out to
be the load-bearing fact behind a second, parallel finding in
`pacer_core.c` - confirmed empirically below, not just inferred from
reading two files side by side.

## Notable finding: a second dead-fallback-branch in `pacer_core.c`, confirmed

`pacer_core_handle_state()`'s single-chamber dispatch (inside
`ST_WAIT_LRL`) is structured as:

```
if (ventricular_paced && !atrial_paced)      { /* V-only branch */ }
else if (atrial_paced && !ventricular_paced) { /* A-only branch */ }
else                                          { /* "pace whichever is due" */ }
```

The final `else`'s own comment explicitly names it as the branch that
handles `"VOO/AOO async: pace whichever is due"`. **It does not.**
`modes.c`'s truth table (the same one cross-checked in
`test_modes.c`) shows every one of the 12 currently-defined modes
satisfies `atrial_paced` XOR `ventricular_paced` (or is dual-chamber) -
meaning AOO and VOO are actually dispatched to the A-only / V-only
branches above it, and the fallback the comment names them for is
never reached by either.

This is proven, not asserted: `test_handle_state_aoo_voo_dead_fallback_finding()`
forces AOO's (irrelevant, per that branch) ventricular timer wildly
overdue and confirms no ventricular pace ever fires - and the mirror
test for VOO's atrial timer. If either mode had actually reached the
fallback branch, that cross-chamber pace *would* have fired, since the
fallback (unlike the A-only/V-only branches) checks and paces both
timers independently. `test_handle_state_fallback_reachable_via_invalid_mode()`
then proves the branch is live code, not literally unreachable code the
compiler could dead-strip - it fires exactly as written when given an
out-of-range `PaceMode_t` value that satisfies neither predicate,
something no real mode does.

This is the same class of comment/code drift already found in
`telemetry.c` and `arrhythmia.c` - a comment that accurately described
an earlier version of the logic (or the author's intent) but never got
updated when the dispatch order or predicates changed underneath it.

## Notable finding: `pacer_core.c`'s "URL safety fallback" depends on an `avi_ms`/`url_ms` ordering that `eeprom.c` never validates

`ST_AVI_WAIT` checks `since_a >= g_avi_ms` (pace, tracking) before
`since_a >= g_url_ms` (pace, safety fallback "if something upstream
misbehaves"). Every one of the 12 built-in `mode_apply_defaults()`
presets sets `avi_ms` well below the default `url_ms` (461ms) - VDD=130,
DDI/DDD=150, DDDR=140 - so the first check always fires first in
practice, making the URL-fallback branch structurally unreachable
**under the built-in presets**.

But `eeprom_validate()` (`eeprom.c`) range-checks `lrl_ms` (300-2000)
and `url_ms` (250-1500) on load, and validates that `mode` is a real
enum value - and never touches `avi_ms` at all, let alone any
relationship between it and `url_ms`. A saved NVRAM block with a
correct CRC and magic, `avi_ms` set above `url_ms`, passes validation
cleanly. `test_handle_state_avi_wait()` models this directly
(`g_avi_ms=1000`, `g_url_ms=400`) and confirms the URL-fallback branch
fires exactly as written. This is a real gap between what `eeprom.c`
guards against and what `pacer_core.c` silently depends on holding -
worth a deliberate decision (add the missing range/relationship check
to `eeprom_validate()`, or document the dependency explicitly) before
Code Generation touches either file.

## The zero-sample and threshold-widening techniques used for `pacer_core.c`

`pacer_core_handle_state()` is public (per `pacer.h`) but reads a
module-local static, `s_cur_sample`, that only `sensing_generate_sample()`
(called only from `pacer_core_tick()`) ever writes. A process that
calls `handle_state()` directly, without ever calling `tick()`, sees a
permanently all-zero sample - and `sensing_is_noise(0, thresh)`
unconditionally returns "yes, noise" for both real thresholds, forcing
`a_sensed`/`v_sensed` to 0 deterministically. That isolates the pure
timing state machine from sensing for most of the suite, with zero LCG
dependency.

The `a_sensed`/`v_sensed`-true branches need real sensing, so a
handful of integration tests drive the actual `pacer_core_tick()`
pipeline instead, under `fake_time.c` (reused from `sensing.c`/
`battery.c`). Their golden tick numbers were captured by a fresh probe
run against this exact linked binary, **not reused from
`test_sensing.c`'s golden data** - `handle_state()` calls
`sensing_is_noise()` an extra time on top of what
`sensing_check_atrial/ventricular()` already do, and `battery_tick()`
consumes its own LCG every tick too, so the effective LCG consumption
sequence differs from `test_sensing.c`'s isolated loop even under the
same seed. A separate technique (widening `g_a_sense_thresh_mv`/
`g_v_sense_thresh_mv` to 9999, or simply using AOO/VOO, which are
unsensed by design) suppresses real sensing while still running the
full `tick()` pipeline, to test `update_refractory_windows()`'s
clearing logic - which only ever runs inside `tick()` - without being
at the mercy of when the random EGM waveform happens to cross a
threshold.

## `main.c`: black-box/subprocess testing, not a linked harness

`main.c` defines its own global `main()`, so - unlike every other file
here - it can never be linked into a test binary alongside a
test-driver `main()` (a straightforward "multiple definition of main"
link error). `test_main.sh` instead builds a separate, standalone,
coverage-instrumented copy of the real `pacemaker_sim` binary (all 8
unmodified `src/*.c` files - the exact same set the top-level
`Makefile` builds, just compiled into `tests/` with `-fprofile-arcs
-ftest-coverage` added) and drives it as a subprocess, asserting only
on stdout, exit code, and the persisted `pacer_nvram.bin` side effect -
there is no internal state to reach from outside a process boundary.
gcov's coverage counters accumulate additively across sequential runs
of the same instrumented binary in the same directory, so every
subprocess invocation in the script - including ones that only probe a
CLI-parsing quirk - contributes to `main.c`'s real, tool-measured
coverage number.

Every expected string and behavior in `test_main.sh` was captured by
running the actual, unmodified binary first and reading its output -
this project's "probe first, then pin" rule applied to a shell/CLI
suite exactly as it was applied to every C suite. One example that
would have been easy to get wrong by reading the source alone: a
sub-1000ms run prints **no periodic status line at all** (it never
reaches `STATUS_PRINT_EVERY_MS`), so an assertion written against a
short 200ms run needed a separate, longer-duration run instead - caught
immediately by actually running it, the same way this project caught
the `sensing.c` index-75-vs-79 miscount and the `arrhythmia.c`
`g_verbose` ordering bug.

## Running it

```
make -C tests -f tests.mk run         # build and run all 8 suites
make -C tests -f tests.mk coverage    # instrumented build + gcov report per module
make -C tests -f tests.mk clean       # remove build/coverage artifacts
```

`test_main.sh` can also be run directly (`./test_main.sh`), as long as
`pacemaker_sim_cov` has already been built in the same directory (the
`tests.mk` targets above do this automatically).

**Consolidated findings across the whole engagement** (all Architecture
& Decoupling Agent inputs ahead of Code Generation):

1. **`telemetry.c`**: `evt_flag_desc()`'s comment claims it only
   describes one flag when several are set; the code actually
   concatenates all of them.
2. **`arrhythmia.c`**: `arrhythmia_run_ams_logic()` indexes the shared
   log ring buffer differently than `telemetry.c` (the module that
   owns it) once the buffer has wrapped - a real, latent cross-module
   bug, not just a style issue.
3. **`modes.c`**: `mode_step()` is dead code - zero call sites anywhere
   in the codebase, despite its own comment claiming it backs CLI
   dry-run checks in `main.c`.
4. **`pacer_core.c`**: a second, parallel dead-fallback-branch finding
   of the same kind as #1/#2 - the single-chamber dispatch's final
   "pace whichever is due" branch, which its comment claims handles
   AOO/VOO, never actually reaches either mode (both are dispatched
   earlier), though the branch is live code for an out-of-range mode
   value.
5. **`pacer_core.c` / `eeprom.c`**: the `ST_AVI_WAIT` "URL safety
   fallback" branch depends on `avi_ms` staying below `url_ms` - true
   for all 12 built-in presets, but never validated by
   `eeprom_validate()`, which range-checks `lrl_ms`, `url_ms`, and
   `mode` but not `avi_ms` or its relationship to `url_ms`.
6. **`main.c`**: the `ST_FAULT` early-exit branch is unreachable via
   any real CLI invocation - consistent with `pacer_core.c`'s own
   comment that this fault path can no longer actually trigger.

None of these were "fixed" - characterization testing's job is to pin
current behavior as a regression net, not to correct it. Each is a
flagged decision point for whoever runs Architecture & Decoupling and
Code Generation next: preserve deliberately, or fix consciously, but
never silently.

The harness pattern used throughout - link the real module against the
real rest of the codebase (no mocks); capture non-obvious behavior via
an actual probe run, never a hand-derived assumption; close coverage

call out genuine findings rather than papering over them - held for all
8 modules, including the two that needed a technique beyond "just link
and call it": `pacer_core.c`'s zero-sample/threshold-widening tricks
and `main.c`'s black-box subprocess harness. Every "probe first, then
pin" catch along the way (the `sensing.c` index-75-vs-79 miscount, the
`arrhythmia.c` `g_verbose` ordering bug, `main.c`'s sub-1000ms

the code, never by reading the source and trusting an assumption.
